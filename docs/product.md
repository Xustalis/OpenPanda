# OpenPanda v0.1.x 产品主线

[English](product.en.md)

**你交代要办什么，Panda 找能干活的设备和 Agent，把结果带回来。**

## 用户为什么要加一层 Panda

如果现有 Agent 或 harness 已经能跑完全程，就继续用它。Panda 首先服务手里已有几种 Agent 或几台设备、却还在手工接力的人。比如本机有代码和对话，构建机有测试环境，两边都能执行各自擅长的工作，结果却得自己去找、去核对。

Panda 的取舍是**在你管理的设备上，用你已有的 Agent，把跨设备的工作作为同一件任务交回来**。设备可以不同，任务的目标、权限和产物需要有清楚的归属。调度和节点中转不依赖 Panda 的托管服务。使用外部模型 API 或 Agent 服务时，相关数据仍受那些服务的数据规则约束。

## v0.1.x 优先打磨什么

1. **交代目标。** 让用户说清要办什么、什么算做完。设备已有明确要求时按要求派发；没有要求时优先选满足条件的简单路径，不为了多机而多机。
2. **派活与恢复。** 按工具、环境和授权筛选执行节点。中断后，只有在具备安全恢复条件时才继续或重新派发。缺权限、缺环境或不能安全重放时，说清卡点，保留需要人工处理的决定。
3. **带回交付。** 从发起端看实际执行位置、步骤、产物、验证状态和剩余事项。需要独立的通过条件时，可用 `panda task add --accept` 把它写成执行端实际运行的检查。未执行、未验证和验证失败应当分开。刷新、重连或重试不能把另一次运行的证据当成本次结果。

桌面入口和网格改进按是否改善这条路径来排序。卫星与更大规模的异构网络是远期方向，不属于 v0.1.x 的部署承诺。

## 用一件事验收这条主线

在笔记本上让 Panda 跑项目测试，带回失败项和原始输出，且不修改源码。先在单机试，再指定一台已配对、装有所需工具和 Agent 的构建机。从原对话看实际执行位置、输出与验证。如果任务中途不可恢复，交付应明确哪些步骤已完成、哪些还缺证据、谁需要做下一步。

这是 v0.1.x 的验收场景，不是一份新的实测报告。已验证的路径、环境和限制见[项目现状](status.md)，运行细节见[执行指南](agent-execution.md)和[路由规则](routing-layers.md)。
