# Real DAG verification

This is an opt-in integration runner, not a fake model test. It calls the real
Claude Code adapter and can incur provider charges. Use a disposable workspace
and a plan generated by an actual model. Keep provider credentials in the native
harness configuration. No credentials are read or printed by this command.

~~~sh
go build -o /tmp/live-dag-verify ./scripts/live-dag-verify
OPENPANDA_ADAPTER_DIR="$PWD/adapters" /tmp/live-dag-verify \
  --root /absolute/new-run \
  --plan /absolute/model-plan.json \
  --source /absolute/input-tree \
  --validator /absolute/independent-validator.py \
  --slots 3 --timeout 40m
~~~

The validator receives the stage ID and runs in its workspace. The operator
must review it: it is trusted executable acceptance, outside agent-write scope.
Do not change it mid-run in a benchmark. Its starting hash and the input plan
hash are written to run.json. The runner refuses an existing runtime.db, uses
private stage directories, and exports task/event/check evidence. It does not
start a network daemon or change the installed Panda configuration. Local tier-2
execution is authorized; the runner does not claim OS sandboxing is enabled.

The production Core performs dependency release, per-agent concurrency, artifact
packing/merging, task state changes and acceptance. There is no fake CLI, result
injection or direct done-state update. No model judge is configured; deterministic
acceptance is separate from subjective visual review. Native provider identities
must be observed from native events, not inferred from the harness name.

For process evidence, independently sample the runner's descendant process IDs
with timestamps while it runs, storing records as processes.jsonl. The format is
shown in scripts/live-dag-metrics.py. Then export read-only metrics:

~~~sh
python3 scripts/live-dag-metrics.py /absolute/new-run > /absolute/metrics.json
~~~

The exporter streams process samples and counts each native PID once per sample.
Its process evidence status is `available`, `missing`, `empty`, or `partial`.
Missing/empty samples produce a null peak, not a measured zero; invalid records
are counted with their first line number without exposing their contents. A
partial file can establish observed overlap but cannot exclude unobserved peaks.
Only sample descendants belonging to this run; unrelated processes are not proof
of task concurrency. Sampling currently identifies Claude processes only.

Dependency checks require a successful producer result before the first consumer
start in both timestamp and database event-ID order. Missing dependencies, duplicate
stage IDs and cycles are reported as graph errors. `all_done` reflects stored
states; `execution_evidence_complete` additionally requires successful results,
valid topology and dependency order. A critical-path bound is emitted only with
that complete evidence. It is separate from `all_final_checks_pass`, which reports
acceptance checks. Keep one plan per run directory.

Never report overlapping process lifetimes as proof of simultaneous provider GPU
compute, theoretical global optimal scheduling, or a matched native-versus-Panda
speedup. Record first-attempt failures and any manually amended recovery plan.

An observed failed row can be a checkpoint awaiting retry. The watcher reads the
recovery assessment and keeps running through retry backoff; it stops on a final
nonretryable failure, review, cancellation, or deadline. A previous version ended
at the transient failed row and interrupted Core's own retry. That experiment
failure must stay in the evidence.

For an explicitly stopped local run, --resume-checkpoint TASK_ID with a
--resume-note can continue a failed local session through the guarded
ReviewWithDispositionAttempt / ResumeApproved APIs. Stop the previous process
first. The new runner takes an exclusive runner.lock, refuses active tasks and
foreign/missing checkpoints, preserves the original run.json and summary.json,
and writes each continuation's exports under continuations/TIMESTAMP. Append
process samples across attempts. This is an explicit operator continuation, not
a claim of unattended crash recovery. Never use it against a production database.
